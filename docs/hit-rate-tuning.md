# 抢票成功率 / 风控调优说明

这份分支（`feat/hit-rate-tuning`）只改一处东西：**把"首发命中时间 / 请求节奏 / 被限流后的恢复策略"调对**。
不改协议、不改安全模型、不改 UI 与配置格式。

改动集中在 6 个源文件 + 测试 + 本文档。

---

## 1. 首发命中时间

### 1.1 预热从 T-5s 挪到 T-30s

`util/Constant.py`：`WARMUP_AT_SECONDS` 5.0 → 30.0。

原来在离开票 5 秒时，在**倒计时同一线程**里触发 `refresh_hot_and_warm()`，
里面是 `fetch_project_payload` + `prewarm_h2_connection` 两个网络往返。
网络一慢就把 `POST /order/prepare` 推到 T0 之后 —— 首发本来就晚一个 RTT，不能再叠加。

### 1.2 连接池预热：保持"只发一个 HEAD"（上游原样）

`prewarm_h2_connection` 只发一个 HEAD，随机点亮池里的一条连接。
> 曾经试过"预热时把整池连接都握手点亮"，但对**短效代理**是负收益：
> 每条代理一被连接就可能开始计费/计时，等于提前烧掉有效期。已按使用反馈撤回。

### 1.3 连接被丢弃时要回填，且关闭要在锁内（保留）

* `_ensure_pool` 从"有池就直接返回"改成"按每个 source 应有多少条补齐"；
* `_discard_slot` 的 `close()` 挪进 `slot.lock`。

原来一次异常就永久少一条连接（池空之前不会重建），并发度会莫名掉到 1/N；
关闭又不在锁内，会打断别的线程正在读的连接，形成"丢一条 → 误伤一条 → 再丢"的雪崩。

## 2. 请求节奏

### 2.1 每次 create 都重算 payload

`task/buy.py`：`_prepare_create_request` 从 batch 外层移进每次 attempt。

原来一个 batch 内 N 次 createV2 共用同一份 `ctoken` / `timestamp` / `ptoken`，
而 ctoken 是一次性风控 token，重放是最直白的机器特征。
顺带修掉 `100034 票价错误` 之后 batch 内仍按旧价继续打的问题。

### 2.2 等待不加抖动（严格按 1000 的整除数）

间隔与 429 的重试都保持上游原样：`time.sleep(interval/1000)`、`time.sleep(rate_limit_delay_ms/1000)`，
精确执行、不加随机抖动。

理由：会员购有「1 秒盾」，同账号同场次每秒只有 1 次有效请求，
社区实测推荐的间隔是 1000 的整除数（200 / 250 / 500ms），目的就是让请求相位稳定地对齐这个窗口；
±25% 抖动会把相位打散，反而降低命中概率。
（曾经加过抖动，按使用反馈已去掉。）

### 2.3 fanout 并发：保持上游语义（每出口 N 条连接并发）

`h2_connections_per_source_ip`（UI 里的「抢票并行数」，默认 3）决定每个出口建几条 H2 连接，
`createV2` 会向**池里每条连接**各发一路，取第一个非 900001 的响应。

> 曾经试过"每个出口只发一路（去重）"以降低判重风险，但按使用反馈恢复上游行为：
> 单 IP 3 并发是上游根据实测调的（`issues#963`：单 IP 上限约 3 req/s，`pr#1058/#1065`：并行数默认 3、作者标注勿改）。
> 现在**没有**任何开关，行为与上游一致。

### 2.4 createV2 的路径随机编码：保持上游原样（默认开启）

上游 `_random_quote()` 会把 `/api/ticket/order/createV2` 随机百分号编码
（例如 `cre%61teV2`、连 `/` 都可能变成 `%2f`），这段来自 `pr#1052`「绕过412风控」，
原作者的说法是"通过随机构造转义 url path，绕过 412 风控机制"，之后随 `pr#1065` 进入主干。

本分支**保持原样**（默认就是开启的，没有开关）：
既然上游是被人实测之后加进来的，先别动；如果哪场跑下来发现它反而带来问题，再单独评估。

### 2.5 三种返回要分开处理（这条是最容易搞错的）

| 返回 | 真实含义 | 正确反应 |
| --- | --- | --- |
| HTTP **429** | CDN 层"没抽中"，请求还没到内层 | **固定短延迟（`rate_limit_delay_ms`，默认 300ms）立刻再打**，不递增 |
| **900001 / 900002 / 221 / 3** | 会员购「1 秒盾」：同账号同场次 1 秒内已发过 1 次有效请求 | 按**正常节奏**继续，不额外退避 |
| **412** | IP（或账号）被限流/封禁 10~15 分钟 | 换出口 / 换账号；单线路走分级退避（见 3.1） |
| 100009 / 100001 / 100034 | 库存不足 / 内部限流 / 票价变了 | 正常失败，按 interval 继续 |

**实测教训**：中间某一版把 900001 也当成"被限速"做了 0.3→0.6→1.2→2.4s 指数退避，
真实一场票（2026-11-12 18:00）跑下来：

- 第 1 分钟只有 **25 次**下单尝试（`--interval 250` 的理论值是 240 次）；
- 相邻尝试间隔中位数 0.99s、最大 5.7s，全程平均 0.74 次/秒；
- 429 约 450 次、900001 约 150 次、100009 约 300 次，而 **412 只有 0 次**（代理池全程 10/10 可用、冷却 0）。

也就是说出口是干净的，纯粹是抽签次数被退避砍掉了一个数量级。现已改为上面这张表的口径。

---

### 2.6 429 连续超时自动换出口 + 整池限速时暂停（本分支新增）

429 是 **CDN 对该 IP** 的限速，与账号无关。上游的做法是"等 `rate_limit_delay_ms` 继续打同一条 IP"——
实测 2026-11-13 那场：某任务单 IP 连续吃到 **1374 次 429**（21 分钟），而它池子里另外 20 条代理
**全程 `可用 21/21、冷却 0`，一次都没被用过**；另一个任务 18 次尝试 **100% 429** 也没换线。

规则（不用固定次数，因为次数和 interval 挂钩）：

| 情况 | 行为 |
| --- | --- |
| 同一条 IP 连续 429 **且持续 ≥`RATE_LIMIT_ROTATE_MIN_SECONDS`(1.5s) 且 ≥`RATE_LIMIT_ROTATE_MIN_COUNT`(3) 次** | 切到下一条出口（不冷却、不计失败） |
| 池子轮过一圈（换满 `可用出口数` 次）仍然全是 429 | 认为整池被限速，暂停 `RATE_LIMIT_ALL_EXHAUSTED_SLEEP_SECONDS`(1.5s) 再继续，避免把所有 IP 一起打进更重的限速 |
| 收到正常业务响应 | 计数与轮转计数清零 |

为什么不能"1 次就换"：429 是概率性放行，不是"IP 被拉黑"（那是 412）。
实测成功样本是**同一 IP 连续 5 次 429 后第 6 发命中**（≈2.2 秒），阈值太低会直接打断这条路径。

换出口是**环形轮转**：`switch_to_next_available()` 用 `(current + offset) % len(states)`，
所以把分配到的 IP 用完会回到第一条继续；处于冷却（412/连接失败）的条目会被自动跳过；
全部都在冷却时返回 False（不切换）。

## 3. 被限流后的恢复策略

### 3.1 412 分级处理

| 情况 | 行为 |
| --- | --- |
| 有多条可用线路 | **把该出口立刻冷却（≥`RISK_CONTROL_PROXY_COOLDOWN_MIN_SECONDS`=600s）+ 换线**，不额外等待 |
| 单线路，第 1~2 次 412 | 等 `RISK_CONTROL_SHORT_DELAY_SECONDS`（1s）重试 —— 也可能只是瞬时抖动 |
| 单线路，第 3 次起 | 指数退避 30 → 60 → 120 → 180s 封顶，并在日志里提示"切换网络/代理；若换出口仍 412 说明是账号级风控，需换账号" |
| 收到正常 JSON 响应 | `risk_streak` 清零（说明没被封） |

为什么多线路要"立刻冷却"而不是等失败阈值：412 是 IP 级封禁（10~15 分钟），
不冷却的话轮换一圈又会选回这个已封的 IP，白白浪费请求；等阈值则每个坏 IP 还要多挨一发。

412 的判定同时改成看 `response.status_code == 412`，不再依赖 `"status=412"` / `"412 风控"`
两次字符串匹配（原来改一个空格就静默失效）。

### 3.2 单线路线路失败也不长睡

`handle_proxy_failure` 在"没有可用备用线路"时，退避上限 `SINGLE_LINE_MAX_BACKOFF_SECONDS = 3` 秒，
不再直接进 `ProxyBackoff` 的 30/60/120/240s。真·线路坏了仍然会记失败、仍然会冷却。

### 3.3 异常分支：保持上游行为（不 sleep）

`JSONDecodeError`（非 412）/ `RequestException` / 通用 `Exception` 仍然只打日志、继续下一轮。
> 曾经给它加过 0.2→3.0s 的统一退避，按使用反馈已撤回，恢复原样。

### 3.4 errno 提取更健壮

`task/buy_helpers.extract_errno()`：取不到或格式非法时返回 -1，
替代原来的 `int(ret.get("errno", ret.get("code")))`（两个键都缺时抛 TypeError，会落到通用异常分支）。

## 4. 代理相关

### 4.1 多任务不再同时打爆同一条 IP（保留）

每个任务是一个独立进程，各自持有一份同一顺序的代理列表，而上游的起始索引固定是 0 ——
N 个任务同时开跑会把**同一条 IP** 瞬间打爆。
现在按列表长度随机选起始线路（单线路无影响），`BTB_PROXY_RANDOM_START=0` 可关闭。

### 4.2 「均匀分配」的实际行为（配置说明）

- **均匀分配（balanced）**：把代理列表轮流平均切分给每个任务（50 条 / 10 任务 = 每任务 5 条），
  但**每个任务只会用自己那份里的第 1 条，直到它失败/冷却才换下一条**。
  也就是说：想同时让多个 IP 干活，只能靠"多任务"或「代理池并发」。
- **代理池并发（local_fanout）**：每个任务拿整池，每次下单对每个出口各发一路。
- **队列模式（queue）**：每个 worker 只拿一条代理，任务内没有备份 IP。

## 5. 参数表

> 上游被明确标注过"**不建议修改**"的只有一处：`pr#1065` 里「抢票并行数」默认 3
> （"给代理池并发增加抢票并行数配置，默认值3（不建议修改）"）。
> 本分支已恢复该默认值，且 `h2_connections_per_source_ip` 的语义与上游完全一致。

| 参数 | 位置 | 默认 | 说明 |
| --- | --- | --- | --- |
| `WARMUP_AT_SECONDS` | `util/Constant.py` | 30.0 | 预热提前多少秒 |
| `RISK_CONTROL_SHORT_DELAY_SECONDS` | `util/Constant.py` | 1 | 412 首次快速重试的等待 |
| `RISK_CONTROL_QUICK_RETRIES` | `util/Constant.py` | 2 | 412 连续几次后转为指数退避 |
| `RISK_CONTROL_BACKOFF_BASE/MAX` | `util/Constant.py` | 30 / 180 | 单线路 412 的指数退避与封顶（秒） |
| `RISK_CONTROL_PROXY_COOLDOWN_MIN_SECONDS` | `util/Constant.py` | 600 | 多线路时 412 命中后该出口的最小冷却（秒） |
| `SINGLE_LINE_MAX_BACKOFF_SECONDS` | `util/Constant.py` | 3 | 单线路"线路级"失败的最长退避 |
| `DEFAULT_RATE_LIMIT_DELAY_MS` | `util/Constant.py` | 300 | HTTP 429 的固定重试间隔（别调大） |
| `BTB_PROXY_RANDOM_START` | 环境变量 | 1 | `0` = 关闭"多线路随机选取起始代理" |
| `RATE_LIMIT_ROTATE_MIN_SECONDS` | `util/Constant.py` | 1.5 | 连续 429 持续多久才换出口 |
| `RATE_LIMIT_ROTATE_MIN_COUNT` | `util/Constant.py` | 3 | 换出口所需的最少连续 429 次数 |
| `RATE_LIMIT_ALL_EXHAUSTED_SLEEP_SECONDS` | `util/Constant.py` | 1.5 | 整池都被 429 时的暂停秒数 |

界面原有参数语义不变，照常可调：`--interval`（每次失败后的间隔）、
`--create-retry-limit`、`--create-request-batch-size`（现在不影响请求节奏）、
`--h2-connections-per-source-ip`、`--rate-limit-delay-ms`。

## 6. 怎么验证

1. 跑测试：`python -m pytest tests -q`（新增 `tests/test_hit_rate_tuning.py`，纯逻辑不联网）。
2. 看日志关键词：
   * `被风控（IP 级），该出口冷却 600 秒，已切换线路到 ...` —— 多线路 412 处理生效；
   * `被风控，1 秒后重试（若持续 412，请切换网络/代理，或换账号）` —— 单线路快速重试；
   * `连续被风控（第 N 次），退避 X 秒` —— 单线路进入分级退避；
   * `请求被限流(HTTP 429)，0.30s 后继续` —— 429 固定短延迟（不再出现 2.4s 这种）；
   * `[900001] 下单过快，被系统限制` 之后应**紧跟下一次尝试**（不再有"退避"字样）。
3. 关键指标：**第一分钟的下单尝试次数**。间隔 250ms 理论值 240 次、500ms 是 120 次；
   若远低于这个数，说明还有东西在拖节奏。

## 6.5 多实例（多端口）隔离

同机多开时，用 `BTB_CONFIG_PATH` / `BTB_COOKIES_PATH` / `BTB_LOG_DIR` / `BTB_TMP_DIR`
四个环境变量可以做到实例级隔离（`start_ui.cmd` 已按端口自动设置）：

| 内容 | 位置 | 是否独立 |
| --- | --- | --- |
| 配置（间隔/策略/代理/API/通知…） | `config.json` | ✔ |
| 账号登录态（含"当前选中账号"） | `cookies.json` | ✔ 必须独立，否则两个实例会互相改当前账号 |
| 应用日志 / 任务日志 | `logs\` | ✔ |
| gradio 临时目录（上传的配置文件、二维码图） | `tmp\` | ✔（`BTB_TMP_DIR` 为本分支新增的开关，不设时行为与上游一致） |
| 程序本体 / `.venv` | 同一目录 | 共用（只读，无影响） |
| `btb_runs\`（托管任务模式的运行目录） | 程序目录下 | ✘ 仍共用（一般抢票流程不走这条路） |

## 7. 本次**没有**改的

* 协议/接口：没有新增任何 B 站接口调用，请求参数结构不变；
* 安全模型：Web UI 鉴权、日志里的 cookie、TLS 证书校验、更新器校验；
* `isRunning` 死标志 / 进程内取消通道；
* 下单成功后的收尾异常仍可能回流到下一轮（重复下单风险）—— 这个改动面大，建议单独一轮处理。
